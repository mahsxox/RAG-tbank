# RAG-система для анализа финансовой отчетности Т-Банка

Вопросно-ответная система по годовым отчетам Т-Банка по МСФО. Извлекает точные числовые значения из таблиц PDF и формирует ответ с указанием источника: файл, страница, год отчета.

На тестовом наборе из 45 вопросов по трем отчетам нужная страница попадает в топ-3 не менее чем в 80 % случаев.

## Стек

Python, Qdrant (гибридный поиск: dense + BM25), intfloat/multilingual-e5-small, fastembed (BM25 с русским стеммером), BAAI/bge-reranker-v2-m3, GigaChat API, PyMuPDF, LangChain (text splitting), Streamlit, Docker Compose.

## Данные

В репозитории лежат три годовых отчета Т-Банка по МСФО (2023, 2024, 2025), всего 388 страниц: `data/T-bank_MFSO_2023.pdf`, `data/T-bank_MFSO_2024.pdf`, `data/T-bank_MFSO_2025.pdf`.

Источник: раздел «Инвесторам. Финансовая отчетность» на сайте банка, https://www.tbank.ru/about/investors/11/

## Быстрый старт

Нужны Docker Desktop и ключ GigaChat API. Получить ключ: https://developers.sber.ru/docs/ru/gigachat/api/overview

```bash
git clone https://github.com/mahsxox/RAG-tbank.git
cd RAG-tbank
cp .env.example .env    # вписать токен GIGACHAT_CREDENTIALS
docker compose up --build
```

Интерфейс: http://localhost:8501

Первый запуск занимает 5 10 минут: собирается образ, скачиваются модели (около 2.5 ГБ) и индексируются отчеты. Последующие запуски занимают несколько секунд, индекс и модели сохраняются в volumes.

Запуск без Docker для приложения (Qdrant все равно поднимается в контейнере): `scripts/run_local.sh` для Linux и macOS, `scripts/run_local.ps1` для Windows.

## Как работает

Индексация: PDF разбирается PyMuPDF постранично, из текста удаляются колонтитулы и лишние пробелы, страницы режутся на чанки по 800 символов построчно. Для каждого чанка считаются dense-вектор (e5-small) и sparse-вектор (BM25), оба хранятся в Qdrant вместе с метаданными: файл, страница, год отчета, заголовок страницы, полный текст страницы.

Поиск: из вопроса извлекается год и превращается в фильтр по метаданным. Dense-ветка и BM25-ветка возвращают кандидатов, их объединение переранжирует cross-encoder. Найденные чанки схлопываются до уникальных страниц, и в контекст LLM уходят целые страницы с заголовком вида «Отчет МСФО за 2024 год, стр. 7».

Генерация: GigaChat с нулевой температурой отвечает только по приведенным страницам и указывает номер источника.

## Проблемы данных и решения

| Проблема | Решение |
|---|---|
| Колонтитул на каждой странице забивает BM25 одинаковыми совпадениями | Строки, встречающиеся на 30 % страниц файла и чаще, удаляются автоматически |
| Год в вопросе совпадает со всеми страницами отчета | Год используется как фильтр по метаданным, а не как поисковый термин |
| PyMuPDF разрывает таблицы пустыми строками, строка «ИТОГО АКТИВЫ» становилась чанком из двух слов | Нарезка построчно без абзацного разделителя, схлопывание пробелов выравнивания колонок |
| Чанк из середины таблицы не содержит контекста | В индексируемый текст и в текст для reranker добавляется год отчета и заголовок страницы |
| Нужное число лежит в соседнем чанке той же таблицы | Поиск идет по чанкам, а в LLM передается вся страница |
| Bi-encoder не различает «прибыль за год» и «прибыль до налогообложения» | Cross-encoder reranker поверх объединения dense и BM25 |
| Смена эмбеддера ломала коллекцию из-за несовпадения размерности | Имя коллекции включает имя модели, размерность берется из модели |

## Интерфейс

Основная область: чат с историей. Под каждым ответом раскрывается блок «Источники» со страницами, которые ушли в контекст LLM: файл, номер страницы, год отчета, score reranker.

Боковая панель: список проиндексированных файлов с удалением из индекса, загрузка новых PDF с немедленной индексацией, индексация файлов из `data/`, не попавших в базу, число чанков после reranker.

Год отчета определяется из имени файла по первому четырехзначному числу вида `20xx`, например `T-bank_MFSO_2024.pdf`. Файл без года в имени индексируется, но в фильтрации по году не участвует.

## Тестирование качества

```bash
docker compose exec app python db_scripts/verify_retrieval.py --quick
docker compose exec app python db_scripts/verify_retrieval.py --llm
```

Набор: 15 вопросов по отчетам 2023, 2024 и 2025 с эталонными числами, сверенными с PDF (баланс, отчет о прибылях и убытках, совокупный доход), плюс два диагностических вопроса вне зачета: неоднозначная формулировка и термин, которого нет в отчете.

Метрика: после reranker чанки схлопываются в уникальные страницы, вопрос засчитан, если страница с эталонным числом стоит на позиции не ниже третьей. Скрипт печатает ранг по каждому этапу (dense, BM25, reranker, контекст), чтобы было видно, где теряется ответ, и итоговую долю попаданий. Флаг `--llm` добавляет ответ GigaChat на каждый вопрос.

Свои вопросы добавляются в список `TARGETS` в `verify_retrieval.py` в формате `(вопрос, "эталонное число", зачетный)`.

## Конфигурация

`src/config.py`. Через переменные окружения переопределяются `QDRANT_URL`, `DATA_DIR`, `EMBEDDING_MODEL`, `RERANKER_MODEL`, `RERANKER_QUANTIZE`. Основные параметры:

| Параметр | Значение | Назначение |
|---|---|---|
| `EMBEDDING_MODEL` | intfloat/multilingual-e5-small | dense-эмбеддер |
| `RERANKER_MODEL` | BAAI/bge-reranker-v2-m3 | cross-encoder |
| `RERANKER_QUANTIZE` | True | int8-квантизация reranker на CPU, в 2 3 раза быстрее |
| `CHUNK_SIZE`, `CHUNK_OVERLAP` | 800, 150 | нарезка по строкам |
| `DENSE_CANDIDATES`, `SPARSE_CANDIDATES` | 25, 15 | кандидаты из веток на вход reranker |
| `TOP_K` | 8 | чанков после reranker |
| `CONTEXT_PAGES` | 5 | уникальных страниц в контекст LLM |
| `YEAR_FILTER_ENABLED` | True | фильтр по году отчета |

Переменные GigaChat в `.env`: `GIGACHAT_CREDENTIALS`, `GIGACHAT_SCOPE`, `GIGACHAT_MODEL`.

## Производительность

CPU, три отчета, около 1 750 чанков: индексация 3 5 минут, первая стадия поиска менее 0.1 с, reranker 8 12 с с квантизацией и 20 35 с без нее, ответ GigaChat 3 8 с. Память около 3 ГБ.

## Ограничения

Вопросы с терминами, которых нет в отчете (например «выручка» у банка), находят ближайший по смыслу текст, но не число. Неоднозначные формулировки («стоимость активов») решает reranker. Сравнение показателей из двух разных отчетов требует, чтобы обе страницы попали в контекст. Reranker на CPU ограничивает скорость ответа. Сканированные PDF без текстового слоя не поддерживаются.
